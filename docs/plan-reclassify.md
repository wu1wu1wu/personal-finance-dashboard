# 自动分类逻辑重构（逻辑设计稿）

> 状态：**待确认**。本文只定义"一条交易该归到哪一类"的判定逻辑，不含界面与实施步骤。
> 依据：真实账本 176 条（2026-09-01 ~ 10-17，脱敏备份）的回放结果。
> 规则编号（L0-1、L2-2…）用于讨论时指代具体条款。

---

## 1. 目标与不变量

**目标**：消灭"分错"和"乱猜"这两种体验；允许明确标注的「推测」，但绝不假装确定。

| 编号 | 不变量 |
|---|---|
| I1 | 用户显式设过的分类**永不被覆盖、永不被改写** |
| I2 | 没有依据时**必须留白**（待确认），绝不猜 |
| I3 | 每条分类都能回答"**凭什么**"（商户键 / 关键词 / 渠道统计 / 时段金额规则 / 你设的） |
| I4 | 学习**只从可信来源**吸收，渠道推测与时段推测永不固化成记忆 |

---

## 2. 现状的四个病灶（回放实测）

| 病灶 | 数据 |
|---|---|
| **从不肯留白** | 176 条里「待确认」**0 条**；而按引擎重算，42 条本该是待确认 |
| **渠道词抢走店名** | 75 条由平台名（美团/淘宝/拼多多）决定分类；其中 **37 条的说明里写着真店名**，却全部命中"美团" |
| **习惯模型是餐饮推土机** | 会开口的只有 3 个桶（20–50 元 × 10–22 点），**全部预测餐饮**；9 条「推测」记录无一例外全是餐饮 |
| **词表追不上真实商户** | 剥掉渠道词后 61/75 条无解；26 个店名里词表只认得其中一小部分 |

根因一句话：**系统在"没有信息"的时刻（支付通知）做了一次分类决策**，于是错误被包装成确定，待确认列表被抽空。

### 2.1 一个被数据推翻的旧判断（重要）

本文早期版本写过"金额/时段信息量近乎为零"。**这条被回放否定了**：

| 规则 | 支持条数 | 命中 | 纯度 |
|---|---|---|---|
| `15~25 元` 且 `10:00–21:00` → 餐饮 | 12 | 10 | **83%** |
| `15~25 元`（不限时段）→ 餐饮 | 13 | 10 | 77% |
| `15~40 元` 且 `11:00–18:30` → 餐饮 | 11 | 9 | 82% |

结论修正为两点：

- **金额是最强的信号**：20 来块的消费 83% 是餐饮
- **时段只起辅助作用**：主要用来排除清晨（9:52 的 20 元是教育学习）；你的餐饮横跨 11–21 点，靠窄窗口反而会漏 64%
- 但 83% ≠ 确定：反例确实存在（`15.8 元 → 美团单车 → 交通`、`19.9 元 → 居住生活`），所以只能标「推测」

## 3. 术语

| 术语 | 定义 |
|---|---|
| **商户键** | 从交易文本里抽出的"这家店是谁"，如 `塔斯汀`、`云上优家超市`、`湖工大-沌阳大道`。抽不出就是 `null` |
| **关键词** | 词表里的**品类词**，如 `星巴克`、`话费`、`超市`、`转账` |
| **渠道·电商型** | 淘宝、拼多多、天猫、京东、唯品会（在它上面下单＝购物） |
| **渠道·综合型** | 美团、饿了么、抖音、高德（同一平台什么都能买） |
| **依据等级** | 确定 / 推测 / 待确认（见 §6） |

## 4. 判定流程

按 L1 → L7 顺序，**第一个命中即返回**。

### L0 预处理（抽取三样东西）

**L0-1 商户键抽取**

从 `商品说明` 依次剥掉：

1. 前缀 `微信支付:` / `支付宝:`
2. 合并提示 `[2条]` 之类
3. `商户单号XXX` / `订单号XXX` / `订单编号XXX`
4. App 后缀 `美团App` / `饿了么App` / `美团平台商户` / `淘宝平台商户` / `美团收银` / `美团订单`
5. 充值话术 `为138xxxx充值50元`
6. 金额 `¥22.30`
7. 脱敏/打码残留 `****`，以及**独立的 4 位数字**（脱敏后单号后 4 位会残留）
8. 分店括号 `（沌口店）`、`(宁康路店)`
9. 连锁后缀：按 `·` 截断取首段（`塔斯汀·中国汉堡` → `塔斯汀`）

**L0-2 无商户的判定**

命中任一条件 → 商户键 = `null`：

- 文本含 `已支付` / `入账工资` / `已到账` / `您账户` / `已隐藏敏感通知内容` / `理赔` / `转账备注` / `收款方备注`
- 清理后不足 2 个字，或超过 24 个字（说明是整段通知原文，不是店名）
- 清理后只剩平台名 / `微信支付` / `支付宝` / 银行名

> **绝不拿通知原文凑商户键**。第一版原型就是在这里翻车的：`微信支付: 已支付¥19.90` 被当成商户，记忆立刻学进一堆垃圾键。

**L0-3 关键词匹配**

- 在 `交易类型 + 交易对方 + 商品说明` 里做包含匹配
- **渠道词本身不算品类词**（`美团`、`淘宝`… 不参与关键词层，单独由 L5 处理）
- 命中多个时排序：**最长词优先** → 优先级数字 → 命中数量

**L0-4 渠道识别**：文本命中电商型或综合型任一平台名。

---

### L1 你设的（最高优先）

- 条件：`categorySource = manual` 或 `userEdited = true`
- 结果：返回该分类，等级「确定」
- 例外：无。任何回填、学习、重新分类都不得改动它

### L2 资金搬运与收入

- **L2-1 资金搬运**：文本命中 `转账` / `红包` / `提现` / `退款` / `还款` / `零钱通` → 返回「转账」
- **L2-2 收入**：否则，若金额 < 0（负数＝收入）→ 返回「收入」
- 二者等级均为「确定」，且都不计入支出统计
- **为什么排在记忆之前**：退款、还款是**交易性质**，不该被"这家店平时卖什么"推翻（"塔斯汀退款"不该归餐饮）

### L3 商户记忆

- 条件：商户键非 `null`，且记忆表里有该键
- 结果：
  - 该键下**只有一种分类** → 返回它，等级「确定」
  - 该键下有**两种以上分类** → **不投票、不留念**，直接落到 L7「待确认」
- 理由：宁可多问你一次，也不猜你的意图

### L4 品类关键词

- 条件：L0-3 命中了关键词
- 结果：返回该关键词的分类，等级「确定」
- 例外 L4-1：**反例词压过正例词**。规则可带 `excludes`，命中反例则该规则作废。初始反例表：

  | 关键词 | 反例词 | 效果 |
  |---|---|---|
  | 充电 | 充电宝 | 充电宝不归交通（归购物） |
  | 会员 | 视频会员 / 音乐会员 | 会员类归休闲娱乐 |

  反例词的判据：**同一个词在不同语境下会指向不同品类**，且能从真实数据举证。

### L5 渠道

- **L5-1 电商型**：淘宝 / 拼多多 / 天猫 / 京东 / 唯品会 → 返回「购物消费」，等级「确定」
  - 依据是平台性质（在淘宝下单就是购物），不是猜测
- **L5-2 综合型**：美团 / 饿了么 / 抖音 / 高德 → 仅当**全部**满足才返回「推测」：
  - 该渠道在**可信记录**（L1 你设的）里 ≥ 3 条
  - 其中同一分类占比 ≥ 80%
  - 否则继续往下

### L6 时段 + 金额规则（仅用于无商户记录）

- 条件：商户键为 `null`，且命中一条已归纳的「时段段 + 金额段 → 分类」规则
- 结果：返回该分类，等级「**推测**」，并显示依据（"15~25 元、10:00–21:00，历史 12 条中 10 条是餐饮"）
- 为什么**只对无商户记录生效**：有商户时，商户信息永远比金额可靠（`16:23 / 15.8 元` 是美团单车，不能因为金额在区间里就当餐饮）

**规则从哪来**：

| 来源 | 规则 |
|---|---|
| 自动归纳 | 只用「你设的」记录做统计：支持 ≥ 5 条、纯度 ≥ 80% 才成为规则；同一分类最多保留 2 条 |
| 手动添加 | 允许在设置里自己写「时段 + 金额区间 → 分类」，可改可停用 |

在你现有数据上，自动归纳出的唯一规则是：`15~25 元` 且 `10:00–21:00` → `餐饮美食`（支持 12、纯度 83%）。

### L7 兜底

- 以上都不成立 → 返回「待确认」，等级「待确认」
- **不再调用任何黑箱模型**

### 已删除

- ❌ 旧的习惯模型（`金额档 × 时段档` 直接写分类的推土机）
- 它的存量输出按 §9-4 处理

## 5. 商户记忆

### 5-1 存什么

```
商户键（归一化后） → {
  分类,
  命中次数,
  来源: manual | keyword,   // manual 优先于 keyword
  更新时间                    // 仅用于展示与排序，不参与判定
}
```

### 5-2 允许从哪学

| 来源 | 是否入库 | 说明 |
|---|---|---|
| 你手设的分类 | ✅ | 最高可信，一次即生效 |
| 关键词命中的分类 | ✅ | 自动积累，是覆盖率的主要来源 |
| 渠道推测（L5-2） | ❌ | 猜的东西绝不固化成记忆 |
| 时段金额推测（L6） | ❌ | 同上 |

### 5-3 冲突与更新

- 同一商户键出现两种分类 → L3 判「待确认」，**不做多数投票**
- 你改动某条记录的分类 → 覆盖该键的记忆（以你的最新意图为准）
- **历史记录不批量改写**（已确认：改一条只改这一条）

### 5-4 读取顺序

资金搬运/收入（L2）→ 记忆（L3）→ 关键词（L4）。记忆先于关键词，因为"这家店实际是什么"比通用词表更具体。

| 等级 | 来源 | 界面 |
|---|---|---|
| 确定 | L1 你设的 / L2 资金搬运与收入 / L3 商户记忆 / L4 关键词 / L5-1 电商渠道 | 无标签 |

## 8. 明确不做（YAGNI）

- 不做多信号概率模型（金额、时段、商户加权打分）——难解释、难验证
- 不做云端/大模型分类——本应用不联网
- 不为"提高覆盖率"而放宽留白标准
- 不做更细的分类体系（宠物/服饰/人情等）——本轮不动分类维度

## 9. 本轮已定的五项

| # | 问题 | 决定 |
|---|---|---|
| 1 | 改一条分类，要不要改这家店的历史？ | **不改**，只改这一条；记忆更新、历史保留 |
| 2 | 收入类记录怎么归？ | **新增「收入」类别**，金额为负且非转账 → 收入 |
| 3 | 旧数据里 19 条凭空分类要不要重置？ | **不做批量迁移**，保留原样 |
| 4 | 旧的习惯模型怎么处理？ | **取消黑箱模型**；能力改为 §L6 的显式「时段+金额」规则，结果标「推测」 |
| 5 | 工资那条（手设为居住生活）要不要改？ | **要**，迁移时一次性把「金额<0 且分类不是转账/收入」的记录统一改为「收入」 |

> 第 5 条属于**数据修正**而非覆盖用户意图：当时分类里根本没有「收入」这个选项，
> 那些标签是被迫塞进支出口径的。修正只在迁移时执行一次。

### 9-1 关于第 4 条的理解

「旧的习惯模型取消」指的是**机制**取消：不再有黑箱模型自动写分类。
它的存量输出按第 3 条保留不动（不批量重判），但今后同类记录由 L6 的显式规则处理，
输出「推测」而不是「确定」。若你本意是"连这条显式规则也只输出待确认、只作提示"，
需要改回来。

### 9-2 新增「收入」类别的影响面

| 位置 | 需要做的事 |
|---|---|
| 分类常量 | `CATEGORIES` 增加「收入」（图标 + 配色，单测会核对配色对比度） |
| 双语标签 | `categoryLabel()` 的映射是 `satisfies Record<CategoryName, MessageKey>`，漏一个编译不过 |
| 预算页 | 收入不可设预算（需过滤掉） |
| 图表/报告 | 收入不进支出榜、不进分类占比 |
| 统计口径 | `isConsumption()` 已有"转账不算支出"，需扩展到"收入也不算" |
| 明细筛选 | 分类下拉里应包含「收入」，方便查收入记录 |

## 11. 验收标准

- 逻辑层为**无 React 依赖的纯函数**，每个 L 分支与边界都有单测（含反例：渠道词不参与关键词、无商户时必须 null、同键冲突必须留白、时段金额规则只对无商户生效）
- 规则归纳有单测：给定一批已确认记录，能归纳出预期规则；支持/纯度不达标时不产出
- 回放脚本可在真实备份上运行，输出"依据等级分布"与"变化明细"
- 任一改动不得让「待确认」因为无依据的猜测而减少
