# 自动分类逻辑重构（逻辑设计稿）

> 状态：**待确认**。本文只定义"一条交易该归到哪一类"的判定逻辑，不含界面与实施步骤。
> 依据：真实账本 176 条（2026-09-01 ~ 10-17，脱敏备份）的回放结果。
> 规则编号（L0-1、L3-2…）用于讨论时指代具体条款。

---

## 1. 目标与不变量

**目标**：消灭"分错"和"乱猜"这两种体验，接受「待确认」变多。

任何改动都不得违反的四条不变量：

| 编号 | 不变量 |
|---|---|
| I1 | 用户显式设过的分类**永不被覆盖、永不被改写** |
| I2 | 没有依据时**必须留白**（待确认），绝不猜 |
| I3 | 每条分类都能回答"**凭什么**"（命中商户键 / 关键词 / 渠道统计 / 你设的） |
| I4 | 学习**只从可信来源**吸收，猜测永不固化成记忆 |

---

## 2. 现状的四个病灶（回放实测）

| 病灶 | 数据 |
|---|---|
| **从不肯留白** | 176 条里「待确认」**0 条**；而按引擎重算，42 条本该是待确认 |
| **渠道词抢走店名** | 75 条由平台名（美团/淘宝/拼多多）决定分类；其中 **37 条的说明里写着真店名**，却全部命中"美团" |
| **习惯模型是餐饮推土机** | 会开口的只有 3 个桶（20–50 元 × 10–22 点），**全部预测餐饮**；9 条「推测」记录无一例外全是餐饮 |
| **词表追不上真实商户** | 剥掉渠道词后 61/75 条无解；26 个店名里词表只认得其中一小部分 |

根因一句话：**系统在"没有信息"的时刻（支付通知）做了一次分类决策**，于是错误被包装成确定，待确认列表被抽空。

---

## 3. 术语

| 术语 | 定义 |
|---|---|
| **商户键** | 从交易文本里抽出的"这家店是谁"，如 `塔斯汀`、`云上优家超市`、`湖工大-沌阳大道`。抽不出就是 `null` |
| **关键词** | 内置/自定义词表里的**品类词**，如 `星巴克`、`话费`、`超市`、`转账` |
| **渠道·电商型** | 淘宝、拼多多、天猫、京东、唯品会（在它上面下单＝购物） |
| **渠道·综合型** | 美团、饿了么、抖音、高德（同一平台什么都能买） |
| **依据等级** | 确定 / 推测 / 待确认（见 §6） |

---

## 4. 判定流程

按 L1 → L6 顺序，**第一个命中即返回**。

### L0 预处理（抽取三样东西）

**L0-1 商户键抽取**

从 `商品说明` 依次剥掉：

1. 前缀 `微信支付:` / `支付宝:`
2. 合并提示 `[2条]` 之类
3. `商户单号XXX` / `订单号XXX` / `订单编号XXX`
4. App 后缀 `美团App` / `饿了么App` / `美团平台商户` / `淘宝平台商户` / `美团收银` / `美团订单`
5. 充值话术 `为138xxxx充值50元`
6. 金额 `¥22.30`
7. 脱敏/打码残留 `****`，以及**独立的 4 位数字**（脱敏后单号后 4 位会残留）
8. 分店括号 `（沌口店）`、`(宁康路店)`
9. 连锁后缀：按 `·` 截断取首段（`塔斯汀·中国汉堡` → `塔斯汀`）

**L0-2 无商户的判定**

命中以下任一条件 → 商户键 = `null`：

- 文本含 `已支付` / `入账工资` / `已到账` / `您账户` / `已隐藏敏感通知内容` / `理赔` / `转账备注` / `收款方备注`
- 清理后不足 2 个字，或超过 24 个字（说明是整段通知原文，不是店名）
- 清理后只剩平台名 / `微信支付` / `支付宝` / 银行名

> **绝不拿通知原文凑商户键**。第一版原型就是在这里翻车的：`微信支付: 已支付¥19.90` 被当成商户，记忆立刻学进一堆垃圾键。

**L0-3 关键词匹配**

- 在 `交易类型 + 交易对方 + 商品说明` 里做包含匹配
- **渠道词本身不算品类词**（`美团`、`淘宝`… 不参与关键词层，单独由 L4 处理）
- 命中多个时排序：**最长词优先** → 优先级数字 → 命中数量

**L0-4 渠道识别**：文本命中电商型或综合型任一平台名。

---

### L1 你设的（最高优先）

- 条件：`categorySource = manual` 或 `userEdited = true`
- 结果：返回该分类，等级「确定」
- 例外：无。任何回填、学习、重新分类都不得改动它

### L2 资金搬运

- 条件：文本命中 `转账` / `红包` / `提现` / `退款` / `还款` / `零钱通`
- 结果：返回「转账」，等级「确定」；金额为负（收入）时不进入支出统计
- **为什么排在记忆之前**：退款、还款这类是**交易性质**决定的，不该由"这家店平时卖什么"来推翻。例如"塔斯汀退款"必须是转账，不能因为记忆里塔斯汀是餐饮就归餐饮

### L3 商户记忆

- 条件：商户键非 `null`，且记忆表里有该键
- 结果：
  - 该键下**只有一种分类** → 返回它，等级「确定」
  - 该键下有**两种以上分类** → **不投票、不留念**，直接落到 L6「待确认」
- 理由：宁可多问你一次，也不猜你的意图

### L4 品类关键词

- 条件：L0-3 命中了关键词
- 结果：返回该关键词的分类，等级「确定」
- 例外 L4-1：**反例词压过正例词**。规则表里每条可以带 `excludes`（反例词），命中反例则该规则作废。初始反例词表：

  | 关键词 | 反例词 | 效果 |
  |---|---|---|
  | 充电 | 充电宝 | 充电宝不归交通（归购物） |
  | 单车 | 共享单车 | 单车归交通；共享单车另行归交通（示例，按需补） |
  | 会员 | 视频会员 / 音乐会员 | 会员类归休闲娱乐，不算其他 |

  反例词的判据：**同一个词在不同语境下会指向不同品类**，且可从真实数据里举证。

### L5 渠道

- **L5-1 电商型**：淘宝 / 拼多多 / 天猫 / 京东 / 唯品会 → 返回「购物消费」，等级「确定」
  - 依据是平台性质（在淘宝下单就是购物），不是猜测
- **L5-2 综合型**：美团 / 饿了么 / 抖音 / 高德 → 仅当满足**全部**条件才返回「推测」：
  - 该渠道在**可信记录**（L1 你设的）里 ≥ 3 条
  - 其中同一分类占比 ≥ 80%
  - 否则 → L6

### L6 兜底

- 没有商户键、没有关键词、渠道也不够格 → 返回「待确认」，等级「待确认」
- **不再调用任何猜测模型**

### 已删除

- ❌ 习惯模型（金额档 × 时段档）自动写分类
- 若要保留，最多用于**给待确认列表排序**，绝不写库

## 5. 商户记忆

### 5-1 存什么

```
商户键（归一化后） → {
  分类,
  命中次数,
  来源: manual | keyword,   // manual 优先于 keyword
  更新时间                    // 仅用于展示与排序，不参与判定
}
```

> 一个商户键对应一个分类。若同一个键先后被记成两种分类，见 §5-3：判「待确认」，不做多数投票。

### 5-2 允许从哪学

| 来源 | 是否入库 | 说明 |
|---|---|---|
| 你手设的分类 | ✅ | 最高可信，一次即生效 |
| 关键词命中的分类 | ✅ | 自动积累，是覆盖率的主要来源 |
| 渠道推测（L5-2） | ❌ | 猜的东西绝不固化成记忆 |
| 习惯模型推测 | ❌ | 同上（该模型已删除） |

### 5-3 冲突与更新

- 同一商户键出现两种分类 → L3 判「待确认」，**不做多数投票**
- 你改动某条记录的分类 → 覆盖该键的记忆（以你的最新意图为准）

### 5-4 读取顺序

记忆先于关键词（L3 在 L4 之前）。理由：记忆来自"这家店实际是什么"，比通用词表更具体。
资金搬运（L2）先于记忆：退款、还款是交易性质，不该被"这家店卖什么"推翻。

## 6. 依据等级与界面标签

| 等级 | 来源 | 界面 |
|---|---|---|
| 确定 | L1 你设的 / L2 资金搬运 / L3 商户记忆 / L4 关键词 / L5-1 电商渠道 | 无标签 |
| 推测 | L5-2 综合型渠道统计 | 「推测」 |
| 待确认 | L6 | 「待确认」 |

另：**每条都要能展开依据**（"命中商户键「塔斯汀」"、"命中关键词「超市」"、"美团历史上 8 条都是餐饮"）。

## 8. 明确不做（YAGNI）

- 不做多信号概率模型（金额、时段、商户加权打分）——难解释、难验证
- 不做云端/大模型分类——本应用不联网
- 不猜金额/时段——实测信息量近乎为零
- 不为"提高覆盖率"而放宽留白标准

---

## 9. 未决问题（下一步再谈）

1. **改分类后的作用范围**：改一条，是否把该商户键下的历史记录一起改？（现状：记忆会被覆盖，但历史记录不动）
2. **收入类记录的归属**：现有 10 个类别全是支出口径，工资入账曾被归为「居住生活」。
   同一缺口还有 1 条：`美团理赔款 +22.31`（收入）在新逻辑下会落到「推测餐饮」。
   可选方向：引入收入维度，或把 `理赔/入账` 也归入「转账」（资金搬运，不计支出）
3. **校准入口**：待确认怎么批量处理、商户键怎么确认（界面问题）
4. **旧数据迁移**：现有 19 条 `auto`/`guessed` 的凭空分类，迁移时是否重置为待确认
5. **习惯模型的去留**：删除，还是降级为"待确认排序"

---

## 10. 验收标准

- 逻辑层为**无 React 依赖的纯函数**，每个 L 分支与边界都有单测（含反例：渠道词不参与关键词、无商户时必须 null、同键冲突必须留白）
- 回放脚本可在真实备份上运行，输出"依据等级分布"与"变化明细"
- 任一改动不得让「待确认」因为猜测而减少
